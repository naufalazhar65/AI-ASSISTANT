## What this is

Personal AI assistant "Mia" — a command center for personal tasks, reachable from multiple channels (web text+voice, Telegram bot, Discord bot, more later) sharing ONE memory, ONE persona, and ONE tool set. Both a real-time voice assistant (from v1.0) AND a multi-platform chat/automation assistant. Inspired by OpenClaw + Siri/ChatGPT Voice.

## Persona & long-term memory

- Persona files in `apps/web/persona` (`IDENTITY.md`, `DREAMS.md`, `SOUL.md`, `USER.md`) are the **single source of truth** for assistant identity/style and stable user facts. They're loaded server-side (`src/lib/persona.ts`, `loadPersonaPrompt`) and folded into the LLM system prompt every turn, so they persist across server restarts.
- **Live updates (OpenClaw-style)**: the LLM may append a hidden `<persona>` tag to the end of a reply (`<persona>user.name=Naufal;soul.tone=formal</persona>`). `GroqStreamingProvider` strips the tag (never spoken) and writes each entry to the matching file (`user.*` → USER.md, `soul.*` → SOUL.md) via `POST /api/persona` (`src/lib/persona.ts` `upsertPersonaFact`).
- So a user introducing themselves ("my name is Naufal") or asking for a style change ("speak formally") is automatically persisted to `USER.md`/`SOUL.md` and remembered after restart.
- No per-user JSON memory store — the persona .md files are the only memory.

- Choose provider via `NEXT_PUBLIC_AI_PROVIDER` (`mock` default | `groq`). Set `GROQ_API_KEY` in `apps/web/.env.local` (server-side only!) for real voice. See `apps/web/.env.example`.
- `GroqStreamingProvider` (`src/ai/GroqStreamingProvider.ts`) implements `AIProvider` and drives: Whisper ASR → Qwen streaming SSE → Orpheus TTS per sentence.
- `VoiceActivityDetector` (`src/audio`) does energy-based VAD on the live mic; `AutoTurnManager` (`src/ai`) runs the gated hands-free loop — VAD is active in **LISTENING** (records utterances, 1s anti-feedback cooldown) and in **SPEAKING** in "barge" mode (higher threshold + 260ms hold, relies on mic echoCancellation) to trigger a voice interrupt over AI audio. The manual Interrupt button also does FR-007.
- Room: `GROQ_VOICE` (autumn/diana/hannah/austin/daniel/troy). Orpheus is **English + Arabic (Saudi) only**, so Indonesian answers are TTS'ed in English pronunciation; partial STT + true Indonesian TTS are Phase 3/blocked.
- Groq STT/TTS are request-based (no WebSocket streaming) — transcripts are final-only. This is why the API is proxied through Next routes holding the key.

Note: Next.js detected a stray `package-lock.json` in `$HOME`; `outputFileTracingRoot` is set in `apps/web/next.config.js` to silence it. Do not remove.

## Critical architecture decisions (from PRD)

- **AI Provider must be abstracted** via `AIProvider` (`connect`, `sendAudio`, `sendText`, `interrupt`, `disconnect`). UI/audio never couple to a specific provider. Swap by changing the provider instance only.
- **Conversation state machine** is explicit: IDLE → LISTENING → PROCESSING → SPEAKING → (TURN_END → LISTENING | INTERRUPTED → LISTENING). Real state machine, not ad-hoc booleans.
- **ConversationManager** (`apps/web/src/ai/ConversationManager.ts`) is the only place that forwards provider events into the state machine. UI talks to it, not to providers.
- **Audio pipeline** (§14): Microphone → Capture → Noise Suppression → VAD → Streaming → ASR → Conversation Manager → LLM → TTS → Streaming → Speaker. VAD and real audio streaming are Phase 2/3.
- **MVP latency targets** (§16): mic→processing <100ms, user stops→AI starts <500ms, first AI audio <1.5s, interruption detection <200ms.

## Key invariants to preserve

1. AI Provider abstraction — swap providers without changing UI/audio
2. State machine correctness — invalid transitions impossible (`transition` returns null)
3. Interrupt safety — old generation must not interfere with new turn (providers must abort streams on `interrupt()`; see MockProvider `generationId` and GroqStreamingProvider `generationId` + `AbortController`)
4. Latency budget — every new feature must consider its impact on the <1.5s first-audio target
5. Security — API keys server-side only (they live in `/api/*` route handlers), tool calls validated server-side, no client-side privileged calls

## Gotchas

- MockProvider is synchronous; `sendText`/`sendAudio` stream the canned answer via `setInterval`. Do not rely on its timing in tests.
- The mic permission/audio path (`AudioCapture`) requires a browser; it degrades to `denied`/`error` states gracefully.
- `AudioPlayer` decodes WAV chunks queued per sentence; `pump()` is guard-locked (no concurrent playbacks) and fires `onDrained` when the queue empties. `TURN_END` is emitted only after playback drains (UI calls `ConversationManager.finishTurn()`), so long replies never re-open LISTENING while the tail is still spoken.
- vitest runs the state-machine tests (`npm test` = `vitest run`). The two `verify.ts` proofs are kept and still run via tsx.
- Next.js route files may only export valid Route fields — do not export helpers/constants from a `route.ts` (build fails).

## Plugin / tool system (Fase 4, 2026-09-04) — typecheck/lint/build/test green

`apps/web/src/lib/tools.ts` is now a **plugin registry** instead of a flat `TOOLS` array + `executeTool` switch that could drift apart. Core types: `ToolDefinition` (schema, unchanged), `ToolRisk` (`read`/`write`/`delete`/`transaction`/`external`), `ToolContext { userKey, rawUser }`, and the new `ToolPlugin { definition, execute(args, ctx) }`. The registry `toolRegistry` bundles each tool's schema + implementation in ONE object. Public exports are all **derived from the registry** so they can't diverge:
- `TOOLS = toolRegistry.map(p => p.definition)` — what's sent to the model (agent.ts uses `TOOLS`, and `TOOLS.find(t => t.function.name === c.name)` for `requiresConfirmation`).
- `executeTool(call, rawUser)` — parses JSON args, looks up `getTool(call.name)`, dispatches to `plugin.execute(args, { userKey, rawUser })`, returns `Error: ...` on unknown tool. Per-tool error handling lives inside each plugin's `execute` (preserving the old switch's exact per-case try/catch).
- `registerTool(plugin)` — add/replace a tool at runtime (idempotent by name).

**Adding a new tool = adding one `ToolPlugin` object** (definition + execute) to `toolRegistry` — no separate switch, no list to keep in sync, and it's automatically visible to the model (`TOOLS`) and dispatchable (`executeTool`). 23 tools currently registered: web_search, calculate, file_read, write_file, edit_file, exec, exec_write, save_note, list_notes, delete_note, remind_me, create_automation, add_task, list_tasks, complete_task, cancel_task, reschedule_task, list_uploads, read_upload, fetch_url, search_memory, memory_get, send_channel. Note: module-level helper functions (webSearch, evaluateArithmetic, fileRead, fileWrite, fileEdit, saveNote, listNotes, deleteNote, scheduleReminder, fetchUrl, searchMemory, addAutomation, ...) are declared later in the file and referenced by the plugin closures — fine because they run at call-time. `verify.ts` still exercises `executeTool` for calculate/save_note/list_notes/delete_note/file_read/exec/write_file/edit_file/memory_get (green). Kept server-side only (imports `node:fs`).

Both `file_read` and `exec` (`cwd`) use `resolveInSandbox` — a request escapes every root → `Error: path escapes every allowed sandbox root`. `file_read`/`exec` also keep their existing `DENY_SEGMENTS`/`DENY_PATTERNS`/`EXEC_FORBIDDEN_*` guards. `.env.example` documents `ALLOWED_WORKSPACES`; `.env.local` sets it to `flowtest-studio`. `verify.ts` exercises the multi-root sandbox with a temp workspace (absolute resolve succeeds, `../` and `~` and outside paths are rejected).

**Cross-channel `send_channel` (Fase 4, 2026-09-04):** tool (risk `read`, so no FR-014 confirmation — it relays immediately) that sends a message to another registered channel (Telegram ↔ Discord). Backing store is `apps/web/src/channels/pushTarget.ts` — now a **label-keyed registry on `globalThis`**, NOT a module singleton. Reason: bots register from `instrumentation-node.ts` while tools dispatch from route/bundle code, and Next compiles these into distinct webpack modules — a module-level singleton gives each a separate `senders` map, so `send_channel` saw an empty registry even though the bots logged "target registered". Storing the map on `globalThis` (one shared Node process) unifies both bundles. Gotcha: the Discord/Telegram sender targets the owner's last-seen channel, which is only recorded once the owner sends a message since server start — so `send_channel` to Discord fails with "no discord owner channel seen" until the owner chats there first (same as reminder push). Imports of pushTarget are intentionally **relative** everywhere (tools.ts/agent/discord/telegram/automationRunner) so tsx probes resolve; the globalThis state is what guarantees cross-bundle correctness.
